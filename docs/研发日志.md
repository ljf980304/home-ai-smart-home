## 2026-08-25 — 设备模型重构 + 风扇接入 + 卡片统一规范

**对应提交**：`ab4d055`（前端业务一期）、`2f6f99c`（本次）

### 背景

第一期前端业务已落地：Naive UI + Pinia + APIfox mock 的真实 HTTP 链路、设备/总览/场景三页、类型与 service 层、`docs/api/接口清单.md` 契约文档。本期以此为基础，把**设备数据模型**往商用方向加固，并接入第一台真实设备（小米桌面循环扇）。

### 本次做了什么

1. **设备模型重构：按类型判别联合**
   - `Device` 从"扁平可选字段"（`brightness?/temperature?/speed?` 堆在一个接口里）改为**判别联合**：公共属性（id/name/type/room/online/power）+ 各类型专属 `state`。
   - 新增 `LightState` / `AirConditionerState` / `FanState`，`type` 决定 `state` 的形态。
   - 理由：契约先行、面向多人多端开发。判别联合让接口自文档化，后端与将来的米家/Matter 适配层映射关系一目了然；设备类型再多也不污染公共接口。
   - 代价：一次性的类型 / service / store / 视图 / 契约文档同步（此刻代码量小，重构成本最低）。

2. **接入小米桌面循环扇**
   - `FanState` 完整建模：挡位 `windLevel`(1-4)、模式 `mode`(直吹/自然)、左右摇头 `swingH` + 角度 `swingHAngle`(30/60/90/120)、上下摇头 `swingV` + 角度 `swingVAngle`(30/60/90/100)、定时 `timerHours`(0-4h)。
   - 契约、前端、APIfox mock 三处同步为 state 结构。

3. **设备卡片统一规范**
   - 固定高度、四区块布局：顶部行（名称 + 标签，标签右对齐）→ 房间（左对齐）→ 核心操作区 → 「···」更多按钮。
   - 核心操作区**默认显示前 4 个控件、每行一个**；控件总数 ≤ 4 不显示「···」，> 4 显示「···」打开**完整控制弹窗**。
   - 控制项改为**数据驱动**：`DEVICE_CONTROLS` 每类型一份清单（switch / radio / slider 三种控件），调整数组即可配置默认显示项。
   - 新增 `DeviceControlModal`（完整控制弹窗）、`deviceUi.ts`（共享控制清单与交互）。

4. **空调补温度控制**：`setTemperature`（16-30℃ 滑块），卡片直接可用。

### 关键决策

| 决策 | 结论 | 理由 |
|---|---|---|
| 数据模型形态 | 按类型判别联合 | 契约自文档化；为适配层铺路；避免 Device 变"大杂烩" |
| 卡片默认控件 | 4 个 / 超出收「···」弹窗 | 老人友好 + 信息密度平衡；高频操作直达，低频进弹窗 |
| 风扇挡位建模 | `windLevel` 1-4（非 0-100 连续） | 贴合真实设备 4 档物理语义 |
| 分段控件 | `n-radio-group` + `n-radio-button` | naive-ui 2.45.2 无 Segmented 组件 |

### 遇到的问题与解决

1. **APIfox PATCH 返回 200 + 空 body**：`res.json()` 抛错导致设备控制回滚。修复 `http.ts`：空 body 直接返回 `undefined`。
2. **场景接口字段不一致**（mock 用 `active`，契约用 `enabled`）：按契约先行原则，对齐 APIfox 的示例数据。
3. **naive-ui 无 `Segmented` 组件**（2.45.2）：改用 `n-radio-group` + `n-radio-button`，视觉即分段按钮。
4. **判别联合下模板收敛**：灯光/空调/风扇各自读取 `state` 字段，靠 `v-if="device.type === 'fan'"` 等判别在 vue-tsc 中正确收敛。
